# 开发协作流程

[English](development-workflow.md) | 中文

本参考说明定义 VecLeap 团队在这个独立仓库中的开发流程。[开发指南](development.zh.md)负责环境准备和命令；根目录 [AGENTS.md](../AGENTS.md) 负责技术约定及[推送前检查选择](../.agents/skills/dsh-pre-push-checks/SKILL.md)。明确的用户指令可以授权本地合并或部署，但不能替代 PR 的评审或验证。

## 分支职责

- `develop`：开发集成分支。已完成、经评审并通过验证的改动在此集成和验收。
- `master`：稳定发布分支。仅通过经批准的发布合并推进，不直接提交任务改动。
- `feature-*`：用户可见的功能或能力。
- `fix-*`：普通缺陷修复。
- `chore-*`：工程、工具、依赖或文档维护。
- `hotfix-*`：从 `master` 上受影响的发布版本创建紧急修复，并同步回 `develop`。
- `release-*`：可选验收分支，用于发布验收与 `develop` 后续工作并行的情况。

分支名只使用小写英文字母、数字和单个短横线，以字母开头且不以短横线结尾。不使用斜杠、下划线、空格、中文或 `test`、`new` 等含义不明的名称。

旧 `dev_desktop` 和 `feature-*` 分支是历史工作分支，不是永久集成分支。在授权的清理前保留其历史；新工作从 `develop` 继续。

## 日常开发与评审

1. 拉取 `origin`，确认目标文件没有未提交改动，从最新的 `origin/develop` 创建任务分支。
2. 同一任务的提供方、消费方、测试、文档和部署资产放在同一分支。VecLeap Hub 是独立仓库；协调两个仓库的兼容版本，不在仓库之间复制源码。
3. 使用 Conventional Commits：`<type>(<scope>): <subject>`。scope 要具体，subject 使用英文祈使句。一个提交不混入无关改动。
4. 向 `develop` 创建 PR。说明行为变化、兼容性影响、发布或回滚需要，以及实际运行的命令。AI 生成的改动与其他改动采用相同评审要求。
5. 合并前必须获得另一位团队成员的批准及所需检查通过。按改动范围评审 Session 格式兼容性、持久化变更、快照、凭据、沙箱和子进程所有权。
6. 将任务 PR 以 Squash merge 合入 `develop`，集成后删除任务分支。共同文件发生变化时，合并前先与 `develop` 同步。

未经任务或既有会话授权，不直接提交或推送到 `develop`、`master`。不绕过分支保护，不强推共享分支，不在缺少所需批准时合并，不在没有发布授权时发布。

## 验证

选择覆盖待推送差异的最小检查集合，遵循根目录说明和推送前检查选择。不得将未运行的命令或失败的检查报告为通过。相关检查包括：

- 行为变化：聚焦测试、必要的已录制 Session 快照，以及 agent loop 或生命周期变化涉及的两套 SDK 投影；
- 提供商变化：使用相应凭据执行真实 API e2e 测试；
- 构建或发布路径：`pnpm run build` 及对应的产物冒烟；
- 文档：`pnpm run test:docs`、`pnpm run doc-sync`，同步更新双语文件及配对记录；
- 源码级质量或发布：仓库要求的 typecheck、lint、coverage、hygiene 和平台检查。

CI 负责完整覆盖和平台矩阵。仅在明确要求、诊断 CI 或无法缩小范围的全仓改动时运行 `pnpm run check:all`。改变模型或产品用户可见行为的 PR 必须包含必要的免密快照；GUI 变化必须包含根目录说明要求的真实流程 GIF。

不得提交 `.env`、API 密钥、凭据、本地构建产物或本地工具配置。保持 Harness 包、profile、生成文件和发布边界完整。外部可感知的破坏性变更必须在同一改动中写入所属升级指南。

## 发布

1. 指定发布负责人。在 `develop` 完成集成和验收；确认包含的提交、兼容性变化和回滚方案。
2. 创建 `develop` 到 `master` 的 PR，要求另一位成员批准及所需发布检查通过。
3. 使用普通 merge commit 合并。发布到 `master` 时不 Squash 或 rebase `develop`。
4. 从已批准的合并提交构建，按所属包或应用的发布流程打标签。只有获得明确发布授权才发布。
5. 记录标签、源码提交、镜像或产物标识、验证和部署结果。

发布受阻的修复从受影响的 `master` 发布版本创建 `hotfix-*`，经评审和验证后以普通 merge commit 合入 `master`，再以普通 merge commit 同步回 `develop`，避免后续发布重新引入缺陷。如果线上版本落后于 `master`，则从经评审的 hotfix 候选打标签并部署，不带入无关工作。

## 分支保护与 AI 边界

保护 `master` 和 `develop`：要求 PR、另一位成员批准、所需检查通过及评审讨论解决。禁止强推和删除。管理员也遵守这些规则；紧急例外必须获得明确授权并留下记录。

AI 工具在编辑或 Git 操作前检查当前分支和工作区，并遵守相同的任务分支、评审和验证要求。文档本身不会建立远程保护；需单独核验远程默认分支、必需检查、合并方式和发布权限。
